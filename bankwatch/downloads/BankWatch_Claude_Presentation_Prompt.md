# Claude 발표 PPT·대본 제작 요청 — BankWatch 최종본 기준

아래 전체를 Claude 새 대화에 붙여넣는다. 최종 제출 묶음의 PRESENTATION_INPUT_GUIDE.md에 적힌 파일을 먼저 첨부한다. 이 요청은 발표 자료 제작이며 구현 소스·제출 문서를 임의로 수정하는 작업이 아니다.

---

BankWatch 데이터베이스체제 과제의 최종 구현을 설명하는 한국어 발표 PPTX와 발표 대본을 제작해줘. 팀명 BankWatch, 1인 팀 이우석 / 2022112052다. 발표 제한은 **총 10분(600초)**이다. 화면 시연·전환·대기 시간까지 포함하며, 9분 30초의 본 내용과 30초 여유로 설계한다. 별도 시연을 덧붙여 10분을 초과하지 마.

## 1. 먼저 확인할 입력과 범위

1. 첨부된 최신 최종 색인·검증 보고서를 먼저 읽고 소스 ZIP의 SHA-256과 버전을 확인한다. ZIP을 읽을 수 없다면 실제 소스와 증거를 읽었다고 말하지 말고 누락을 알린다. 파일 작업이 가능한 세션에서 압축을 풀어 진행한다.
2. 공식 과제 PPT·최신 공지·교수 피드백, 최종 시나리오·ERD·명세·데이터 사전, 실제 Java/SQL/테스트를 대조한다. 출력물이 오래된 CP1/CP2 후보나 초기 v2 설계를 기준으로 삼지 않게 한다.
3. 최종 세트는 시나리오 v1.11, ERD·명세·데이터 사전 v1.10(무변경)이다. 전체를 v1.11 검토 세트로 지칭할 수 있지만 개별 문서 버전을 바꿔 말하지 않는다.
4. 첨부된 파일 목록·SHA·검증 상태를 첫 결과에 간단히 적는다. 코드와 문서가 충돌하면 발표 문구로 감추지 말고 파일·행·차이와 영향부터 보고한다. 실제 결함이 있을 때만 별도 수정안을 제시하고, 이 발표 작업에서 프로젝트를 새로 설계하거나 범위를 늘리지 않는다.

## 2. 발표에서 반드시 설득해야 할 세 가지

**왜 이 도메인인가:** 정보보안 사고 대응을 단순 탐지 결과 표시로 끝내지 않고, 근거 확인→담당자 배정→계정 보호→종료 및 이력으로 연결하는 업무를 직접 구현하려고 선택했다. 정상 기기 변경과 조사 후보는 신규 기기 성공 한 건만으로 구별할 수 없고 이전 실패 기록의 시간적 맥락이 필요하다. 경보는 조사 후보이지 실제 부정접속 확정 판정이 아니다.

**왜 DB인가:** 같은 원본 이벤트를 근거로 재현해야 하고, 재탐지·동시 요청에도 경보가 중복되면 안 된다. 담당자 두 명의 동시 선점, 같은 담당자의 오래된 화면 갱신, 계정 잠금과 조치 이력의 일부만 저장되는 문제를 막아야 한다. 이 업무 요구를 PK/FK/UQ/CHECK, JOIN·윈도우 질의, 트랜잭션·행 잠금·버전 검증, 파티션·인덱스의 필요성과 각각 연결한다. “데이터가 많아서”, “저장이 편해서”만으로 설명하지 않는다. CSV는 수집 입력이며 관계·제약·원자적 대응은 PostgreSQL이 담당한다는 구체적인 예를 쓴다.

**원래 요구를 어떻게 구현했는가:** 요구사항→실제 구현→확인 증거의 대응을 보여준다. 최소한 기능4개, SQL 요건, 정규화·키·제약, 예외 시나리오, 트랜잭션·동시성, 함수200줄 제한을 포함한다. REQ/FEAT/FUNC/QRY/TEST 번호는 최종 XLSX·소스에서 확인한 것만 사용한다. 가짜 함수·질의 번호를 만들지 않는다. PPT 본문에는 대표만 넣고 전체 대응표는 별도 부록 MD에 담는다.

## 3. 교수 피드백을 반영한 결정 — 반드시 설명

- **수집·탐지 위치 결정:** 가상 모바일뱅킹 인증 서버가 이미 처리한 성공/실패 결과를 CSV로 만든다. ADMIN이 입력하며 BankWatch 응용 서버가 저장된 결과를 PostgreSQL SQL로 사후 분석한다. 실제 은행 서버 연결, 실시간 패킷 감시, DPI, 문자·전화 내용 분석을 구현했다고 쓰지 않는다. 입력 원본이 가상이라는 점을 밝히되 본문을 한계 설명만으로 채우지 않는다.
- **기능 축소:** 현재 FEAT-01 운영자 인증, FEAT-02 로그 입력·조회, FEAT-04 R02 탐지·근거, FEAT-06 사건 대응이다. 초기 R01·5분·같은 IP 조건, 규칙 편집·버전 관리 화면, 개인 저장 검색, 검증 센터 등을 현재 기능으로 소개하지 않는다. IP 검색이나 로그 입력 이력 테이블 등 실제 없는 속성·기능도 추가하지 않는다.
- **SQL 윈도우 탐지:** R02 하나, 같은 고객의 고정10분 구간에서 신규 기기 성공보다 **엄격히 앞선** 실패5건 이상. 같은 시각 실패 제외. 후보 중 발생 시각·이벤트ID 순 첫 성공을 대표로 선택. 실제 Java SQL에서 사용한 CTE·윈도우 프레임과 동시각 처리 방식을 확인해 그림과 소량 SQL로 설명한다. 이동10분 또는 5분으로 바꾸지 않는다.
- **중복·원본·분할:** 경보 UNIQUE(rule_id,account_id,bucket_start), 원본 PK(occurred_at,event_id), 근거의 전체 복합FK, KST 월별 RANGE(2026년10·11·12월)를 표시한다. 월별 저장 파티션과 탐지10분 구간은 서로 다른 목적이다.
- **상태 변화 구체화:** 사건은 미배정(사건없음)→조사중(closed_at NULL)→종료(closed_at 존재), 계정은 접근가능(lock_incident_id NULL)↔보호잠금(원인 사건 참조)으로 **별도 두 그림**을 그린다. 행위자·조건·커밋 결과·실패 시 유지 상태를 실제 코드에 맞춰 표시한다. 사건 종료가 자동 계정 해제라는 잘못된 화살표를 넣지 않는다. ADMIN은 종료 후에도 원인 사건에서 해제할 수 있다.
- **200줄 제한:** 직접 작성한 함수·메서드·테스트는 선언부터 마지막 줄까지200줄 이하. 파일이나 클래스 전체가200줄 이하라는 뜻이 아니다. 최종 검사에서 확인한 최대값과 범위를 적고, 생성 Wrapper와 직접 작성 소스를 구분한다.

슬라이드에 내용을 과밀하게 넣지 않는다. 4장의 상태도와 ERD가 작아지면 관계의 핵심만 본문에 쓰고 전체 ERD는 별도 참고자료로 제공한다. 위 시간을 실질적으로 지킬 수 없는 경우 먼저 내용 밀도를 줄인다. 발표용 본문9장에 부록을 더하더라도 부록은 필수 발화에서 제외하고 시간을 늘리지 않는다.

7장80초에는 로그 입력→탐지→원본근거→담당자 선점/보호→이력 순서만 시연한다. 모든 예외 시험을 현장에서 다시 수행하지 말고6·8장에서 증거로 설명한다. 현장 준비가 불안하면 동일 구현의 확인된 캡처로 대체한다. Pages 체험판을 사용하면 브라우저의 가상 데이터 시뮬레이션이라고 명시한다. Pages 화면이 Java/PostgreSQL 서버를 실행한다고 설명하지 않는다. 실제 PostgreSQL 원자성·잠금 근거는 로컬 앱 검증 기록으로 설명한다.

## 5. 사실과 검증 수치

- 정상7건: 후보2, 대표 성공ID6, 경보1, 근거6, 재탐지 신규0. 후보2가 경보2가 되는 것처럼 쓰지 않는다.
- SC-02: 서로 다른 관제 담당자 두 명의 선점 경쟁, 그 다음 승자 한 명의 독립 두 세션에서 버전 경쟁. 각각 성공1·충돌1. SC-03: 첫 정상INSERT 후 없는 고객 조회가 실패해 입력파일 전체 롤백. 직접FK제약 시험은 TEST-09이며 SC-03을 대신하지 않는다. SC-04: 커밋 전 실제 연결 종료 후 조치·상태·이력 전부 롤백.
- 보존된 Windows B1/B2: Java21/Boot4.1.2/Maven3.9.16/PostgreSQL16.16, 표준 빌드의PG시험0과 별도 postgres-it JUnit10(실패0/오류0/건너뜀0), 실제 JAR HTTP48요청·132검사를 구분한다. 10+48+132를 합쳐 “190개 시험 통과”라고 하지 않는다.
- Claude CP2의SQL수준 시험37/37, 동시성15/15, 직접 계산 비교13/13은 SQL상수와 서비스순서를 재현한 별도 시험이며 JUnit·HTTP 재실행이 아니다. CP3 포장은 이를 재실행하지 않았다.
- 최신 Codex 검증 결과가 추가 첨부되면 해당 실행의 환경·대상·결과를 별도로 확인해 쓴다. 소스37개 해시 일치는 과거 실행 증거와 현재 실행 코드를 연결하며, 현재 전체 검증을 다시 실행했다는 뜻은 아니다.
- 인덱스는 같은 질의·바인딩·데이터의 전후 계획을 비교했다는 사실을 설명한다. 측정 근거 없는 속도 향상 비율이나 보장 문구를 만들지 않는다.
- 명세 항목수10/4/10/23/11, 대표SQL8개 이상/업무JOIN3개 이상/집계2개 이상/CTE·윈도우 사용 여부는 최종 실제 파일에서 대조한다.

## 7. 진행 방법과 끝 보고

먼저 읽은 파일과 최종 기준선, 핵심 메시지,9장 구성과 시간표를 확인한 뒤 곧바로 실제 파일 제작까지 진행한다. 초안 설명만 하고 중단하지 않는다. 불필요한 재설계와 기능 추가를 하지 않는다. 파일생성 도구가 없으면 그 한계를 명확히 말하고 만들었다고 주장하지 않는다. 최종 보고에는 생성 파일·실제로 검사한 것·실행 못한 것·사용자가 확인할 리허설 한 가지를 짧게 적는다. 사용자의 코드/원본문서/이미 배포된 사이트는 이 발표 작업에서 변경하지 않는다. 새 검증이나 버전은 근거 없이 지어내지 않는다.
