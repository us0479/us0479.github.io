2. 프로젝트명과 개요

프로젝트명: BankWatch — 모바일뱅킹 인증 결과 로그 기반 이상접속 탐지 및 사건 대응 관리

가상 모바일뱅킹 인증 서버가 로그인 성공·실패를 확정할 때 남긴 결과 로그를 받아, 보안관제 담당자가 원본 근거를 확인하고 사건을 조사·보호·종료한 이력을 관리하는 웹 시스템입니다. 정상 고객도 휴대전화를 바꾸면 신규 기기 성공이 생기므로, 신규 기기 성공 한 건만으로 사고로 단정하지 않고 같은 고객의 앞선 실패 기록과 함께 조사 후보를 판단합니다.

교수님 피드백에 따라 데이터가 어디서 생기고 어디서 탐지하는지를 구체화했습니다.
- 생성: 가상 인증 서버가 로그인 결과를 확정하는 순간 이벤트ID·고객참조·발생시각·기기참조·성공/실패를 기록합니다. 성공이면 그 기기가 처음 본 기기인지도 인증 서버가 판정해 함께 기록합니다. 실제 서버는 없고 샘플 CSV로 재현합니다.
- 수집: 관리자(ADMIN)가 이 UTF-8 CSV 파일을 관제 웹 화면에서 BankWatch 응용 서버로 업로드합니다. 파일 단위로 저장하거나 전부 취소합니다.
- 탐지: 관리자가 10분 경계의 기간을 지정해 요청하면 BankWatch 응용 서버(Spring Boot)가 PostgreSQL 질의로 사후 탐지합니다. 브라우저는 계산하지 않습니다. 실시간·자동 주기 탐지는 하지 않습니다.
- 범위 밖: 실제 은행 인증 서버 연동, 네트워크 감청·DPI, 휴대전화 문자·통화 수집, 실제 계정 차단·이체. 보호 잠금은 DB에 기록하는 가상 접근 상태입니다.

이 도메인을 고른 이유는 보안관제에서 "경보가 떴다"로 끝나지 않고, 나중에도 어떤 원본이 근거였는지, 누가 사건을 맡았는지, 왜 계정을 보호했는지, 어떤 판정으로 끝냈는지를 같은 답으로 재현해야 하기 때문입니다. 여러 담당자가 같은 경보를 동시에 다루고 처리 도중 실패도 생깁니다. 그래서 원본·고객·경보·근거·담당자·사건·보호 원인·버전·처리 이력을 DB에서 키와 제약으로 연결하고, 중복 입력·동시 선점·갱신 손실·중간 실패에서도 반쪽 변경이 남지 않게 하는 것을 핵심 목표로 삼았습니다.

3. 주요 구현 기능

1) 운영자 인증과 권한
BCrypt 비밀번호·세션·CSRF와 서버의 현재 역할 검사로 관리자(ADMIN)와 관제 담당자(ANALYST)를 구분합니다. 관리자는 로그 입력·탐지·보호 해제를, 담당자는 미배정 경보 선점과 자신이 맡은 조사 중 사건의 보호·종료를 수행합니다. 이력의 실행자는 요청 값이 아니라 로그인 세션에서 얻습니다.

2) 인증 결과 입력·검색
CSV 6개 필드(event_id, customer_ref, occurred_at, device_ref, event_type, is_new_device)를 입력합니다. 성공은 신규 기기 true/false가 필수이고 실패는 비워 둡니다. 같은 키·같은 내용의 재입력은 중복으로 세어 건너뛰고, 같은 키의 다른 내용이나 없는 고객 참조가 나오면 그 파일에서 새로 넣은 기록 전체를 취소합니다. 고객·결과·기간 조건 검색, 정렬·페이지네이션, 10분 구간·결과별 집계를 제공합니다. 현재 로그에는 IP 컬럼과 IP 검색이 없습니다.

3) 단일 규칙 R02 탐지와 근거
같은 고객의 고정 10분 구간에서 신규 기기 성공보다 시각이 엄격히 앞선 실패가 5건 이상이면 조사 후보입니다. 성공과 같은 시각의 실패는 세지 않고, 발생 시각·이벤트ID 순서의 첫 적격 성공을 대표로 고릅니다. PostgreSQL CTE와 윈도우 함수(date_bin, count FILTER OVER … EXCLUDE GROUP, row_number)로 구현했고, 대표 성공과 선행 실패를 원본 전체 복합키로 경보 근거에 연결합니다. 기본 7건 입력의 결과는 후보 2·대표 성공 ID 6·경보 1·근거 6이고, 같은 기간을 다시 탐지해도 새 경보는 0입니다. 실패 4건 뒤 성공, 기존 기기 성공, 다른 구간·다른 고객 등 경계 입력 41건은 경보 0입니다.

4) 사건 조사·대응
담당자는 경보를 선점한 뒤 원본 근거와 모의 본인 확인으로 조사하고 보호 잠금·종료 판정(사고 확인·정상 행위·판단 보류)을 남깁니다. 배정·보호·관리자 해제·종료마다 사유와 실행자를 이력으로 저장합니다. 사건의 미배정→조사 중→종료와 계정의 접근 가능↔보호 잠금을 서로 독립된 두 상태도로 정리했고, 상태 문자열을 따로 저장하지 않고 사건 유무·종료 시각·잠금 원인으로 계산합니다. 사건을 종료해도 보호는 유지될 수 있으며, 관리자는 종료 후에도 현재 잠금 원인 사건에서 해제할 수 있습니다.

4. 트랜잭션·동시성 제어가 필요한 지점

- 파일 입력, 경보·근거 저장, 사건 생성·배정 이력, 계정 보호 원인·사건 버전·조치 이력을 각각 하나의 업무 트랜잭션으로 묶습니다.
- 파일 입력(READ COMMITTED): 첫 행을 정상 INSERT한 뒤 다음 행의 고객 조회가 실패하면 앞의 INSERT까지 전체 롤백합니다(SC-03). 직접 FK 위반은 별도 시험으로 구분했습니다.
- 탐지(REPEATABLE READ): 후보 계산과 근거 저장을 같은 스냅샷에서 수행하고, 경보 UNIQUE(rule_id, account_id, bucket_start)로 재탐지·동시 탐지의 중복을 막습니다. 원본은 발생 시각 기준 KST 월별 RANGE 파티션과 PK(occurred_at, event_id), 근거는 원본 전체 복합 FK로 연결합니다.
- 동시 선점: 서로 다른 담당자 A·B가 같은 경보를 맡으면 경보 한 행 잠금과 사건 UNIQUE(alert_id)로 한 명만 저장합니다(SC-02).
- 갱신 손실: 조치는 고객→사건 순서로 행을 잠근 뒤 담당자·현재 상태·기대 버전·잠금 원인을 다시 확인하고 버전 조건으로 갱신합니다. 같은 담당자의 두 세션이 같은 버전으로 보호하면 한 요청만 성공합니다(SC-02).
- 처리 중단: 보호 원인과 버전을 바꾼 뒤 COMMIT 전에 실제 DB 연결을 종료해도 이전 상태로 복원되고, 사용자가 다시 요청해야만 반영됩니다(SC-04). 연결 종료 권한(pg_signal_backend)은 시험용 검증 역할에만 부여하고 앱 DB 역할에는 부여하지 않았으며, 앱 코드는 연결 종료를 호출하지 않습니다.
- 교착이 실제로 발생하면(40P01) 전체 업무를 새 트랜잭션으로 다시 실행합니다. 월별 파티션 제외와 후보 인덱스 추가 전후 실행 계획을 같은 데이터·같은 질의로 비교했으며, 성능 향상을 미리 성공 조건으로 가정하지 않았습니다.

5. 개발 환경

- DBMS: PostgreSQL 16
- 응용 프로그램: Java 21, Spring Boot 4.1.2, Spring Security, Spring JDBC(NamedParameterJdbcTemplate, 값 바인딩), Maven Wrapper 3.9.16, HTML/CSS/JavaScript 관제 화면
- 설계: 논리 테이블 8개(operator_user, customer_account, security_event, detection_rule, alert, alert_event, incident, incident_history), 44컬럼, PK/FK/UNIQUE/NOT NULL/CHECK와 대표 근거 부분 UNIQUE. 함수 종속·정규화 근거를 문서화했고, 대표 표시(is_anchor)의 의도적 파생 중복은 따로 설명합니다.
- 직접 작성한 함수·메서드·테스트·익명 함수는 선언부터 마지막 줄까지 200줄 이하로 관리합니다.

교수님 피드백과 기능 축소
- 초기 등록(2026-11-03)의 IP 기반 규칙, 고정 5분, 복수 규칙, 규칙 편집·버전 관리, 탐지 실행 이력, 개인 검색 조건 저장, 고객 활동 타임라인 등 편의 기능을 줄이고, 단일 R02·고정 10분과 원본 근거·사건 대응의 무결성에 집중했습니다. 실패 반복 자체보다 앞선 실패와 신규 기기 성공의 조합을 조사 대상으로 삼고, 1인 과제에서 입력·근거·중복·대응의 연결을 끝까지 검증할 수 있도록 범위를 한정했습니다. 10분·5건은 이 프로젝트의 고정 데이터 계약이며 실제 은행 운영 임계값이라고 주장하지 않습니다.
- 탐지를 SQL 윈도우 질의로, (규칙·고객·구간) UNIQUE와 로그 발생 시각 월별 파티셔닝을 적용했습니다.
- 데이터 출처·수집 방식·탐지 주체와 시점을 위 2번처럼 구체화했고, 사건·계정 상태도와 운영자·응용 서버·PostgreSQL 사이의 잠금·커밋·롤백 시퀀스를 문서에 그렸습니다.

검증 상태: Windows의 실제 Java 앱과 별도 PostgreSQL 16에서 통합 테스트 10개와 인증 HTTP 48요청/132검사가 통과한 기록이 있습니다(수치는 합산하지 않습니다). GitHub Pages에는 가상 데이터로 동작하는 별도 브라우저 체험판과 공개 소스를 두었으며, Pages에서 Java/PostgreSQL 서버가 실행되는 것은 아닙니다.

전체 흐름은 '가상 인증 결과 입력 → 앞선 기록 기반 R02 탐지 → 원본 근거 확인 → 담당자 조사·보호·해제·종료 → 결과 이력 보존'입니다. 위 주제로 데이터베이스체제 프로젝트를 등록합니다.
